# 8-hour soak — memory bounded, and two things it caught that were not the point

**Build:** production, `V=1.1.0-beta;R=7a0b70c;CAP=USB`. **Date:** 2026-09-06/07.
**Fixture:** `scripts/phase9_soak.py`, 8.00 h, WiFi off for the first 4 h then on.
**Raw:** `private/2026-09-07-run0089-session.csv` (936 rows), soak JSONL in the
session scratch. Device kept running on battery after USB was pulled, so
`run0089` covers **15.6 h in one boot**: 8 h of back-to-back sweeps, then 7.6 h
idle. The idle tail was accidental and turned out to be the most useful part.

## The gate: passed

4,112 laps, **0 failures (0.0%)**. Home restored to 910.525 MHz on every lap.
Every drop and error counter finished at zero: `queue_drop`, `row_drop`,
`bus_miss`, `bus_contention`, `nmea_bad_crc`, `gps_oversize_drops`, and all four
`*_observation_drops`. 11 CRC errors against 5,147 packets received.

**Memory is bounded, and the idle tail is what proves it.** Free heap moved in
exactly two discrete steps and then did not move again:

| Uptime | heap_free | Cause |
|---|---|---|
| 0.00 h | 257,200 | boot |
| 0.02 h | 210,728 | −46,472 — UI canvas + task startup |
| 4.02 h | 153,928 | −56,248 — WiFi AP starting, on schedule |
| 4.67 → 15.35 h | **153,928, unchanged** | 10.7 h flat |

`heap_largest` tracks it identically (143,348, flat), and the largest/free ratio
only moves from 0.955 to 0.931 across the whole run — no fragmentation trend.
A leak would have shown in the 7.6 h idle tail, where nothing was allocating and
the value simply did not change.

WiFi on cost the sweep essentially no radio time: Pass-A median 833 ms → 847 ms.

## Finding 1 — Pass-B spent 3.9 hours and promoted nothing

`PBA=15680, PBD=0`. Sweep away-time is dominated by Pass-B, not by the sweep:

| Peaks in a lap | Median away | Laps |
|---|---|---|
| 0 | **833 ms** | 3,024 |
| 1 | 11,643 ms | ~225 |
| 2 | 17,512 ms | ~152 |
| 3 | 25,824 ms | 12 |
| 5 | 44,860 ms | 2 |

15,680 attempts ÷ 1,568 peaks = exactly 10.0, matching
`PASS_B_SF_BW_CANDIDATE_COUNT`. Aggregate: the radio was away from Watch **60.8%
of the run**, and **80.2% of that away time was Pass-B** — 3.90 h of the 8.

Using this project's own measured result that reception loss is proportional to
away time and nothing else (phase12 §6.3, predicted 0.459 vs measured 0.463),
being away 60.8% implies roughly **2,650 packets not heard** over the run, for
zero promotions.

**This is not a defect report.** Pass-B promotes *off-grid* packets at peak bins
on candidate SF/BW; the 1,711 packets Watch decoded were on the home channel and
are not candidates for promotion. Zero may be the correct answer if there is no
off-grid LoRa on those bins at this location. What the run establishes is the
cost side of a cost/benefit question, measured rather than assumed, at one
location over 8 hours. It belongs to Workstream 17's sampling review.

## Finding 2 — the UI task was at 93% of its stack

`ui_stack_free` read **288 bytes of 4,096** — a high-water mark reached within
the first two minutes and never moved for 15.6 h. It did not overflow. But 93%
utilisation is not margin, and this project has already had one real stack
overflow (`logger_task`, Phase 9) plus a documented ui_task crash from putting a
~5.5 KB `WaterfallHistory` on this same stack.

`-fstack-usage` on the shipped build found why — draw functions were holding
snapshot structs as stack locals:

| Function | Frame before | After |
|---|---|---|
| `drawMeterPage` | 960 B | 192 B |
| `drawChannelPage` | 848 B | <150 B |
| `drawNodesPage` | 800 B | <150 B |
| `drawCapturesPage` | 736 B | 224 B |
| `drawActivitySummary` | 704 B | <150 B |
| `drawWaterfallPage` | 608 B | <150 B |

`CaptureHistory` is 516 B, `NodeRoster` 672 B, `ScopeTrace` 256 B, `WaterfallRow`
236 B. Only `ui_task` ever draws, so all eleven are now function-static: BSS
instead of stack. **Worst draw chain 1,312 B → 592 B**, RAM 18.3% → 19.8%.

The important caveat: 288 B is the deepest path *actually exercised*, and the
device sat on one card for most of the run. Pages never displayed contributed
nothing to that watermark, so the true worst case before this change was
somewhere below 288 B of headroom, not at it.

## Finding 3 — the redraw instrumentation overflowed

Added the day before, and this run caught it. `ui_redraw_mean_us` fell from
62,781 to 5,306 at 8.01 h, which a cumulative mean cannot do: `uiRedrawTotalUs`
was a uint32 of microseconds and wrapped. At the measured ~2.6 fps and ~62 ms
mean it accumulates ~161,200 µs/s, wrapping in **7.4 h** — matching where it
broke. Now uint64, with the frame count exposed so a host can difference two
samples for a windowed mean instead of trusting a since-boot average.

The max was unaffected (running maximum, no accumulation): **223 ms worst
frame**, last increased at 4.92 h and flat through the remaining 10.7 h
including the entire idle tail. So redraw cost is bounded.

What this does **not** answer is whether the card-view rebuild made frames more
expensive — there is no pre-change baseline to compare against. What it does say
is that the worst frame is bounded, stopped growing, and runs on Core 0, which
never touches the radio, so it cannot cost a packet.

## Not verified here

The stack fix, the uint64 fix, and the widened session-row buffer are all built
and host-tested but **not yet flashed** — the board was disconnected to read the
card. The next run should re-check `ui_stack_free` after deliberately walking
every card view, which is the measurement this run could not make.
